# S04 — Live forecasts via Open-Meteo

**Epic:** core value · **Depends on:** S03 · **Spec refs:** [04-data-sources](../specs/04-data-sources.md), [01-architecture](../specs/01-architecture.md), [06 Slice 2](../specs/06-implementation-plan.md)

> As a camper, I want window recommendations based on the live 16-day forecast, so that the answer reflects reality and stays current without me doing anything.

## Description

The Open-Meteo adapter (batched multi-point call, chunked ≤100 coordinates, digest math), the KV store adapter, and the steps of the 2-hourly `refresh-weather` workflow (read site list → one fetch+digest step per chunk, with retries → final step writes `wx:digest:v1`). The cron `schedules` for both bindings exist in `wrangler.jsonc` but are commented out: Cloudflare's API 403'd the field at S01 time (feature GA'd 2026-06-02, apparently not yet rolled out to this account — S01 notes); re-enabling them is part of this story. The read path switches from fixture to KV. Staleness handling lands. The campsite list is a hardcoded constant of ~10 real sites (Reykjavík, Þakgil, Húsafell, Akureyri, Mývatn, Egilsstaðir, Höfn, Skaftafell, Ísafjörður, Vestmannaeyjar). First production data lands here.

## Acceptance criteria

- [x] Adapter contract test against a recorded multi-point Open-Meteo fixture: per-site splitting of the response array, units (°C, mm, km/h), `cloudMeanDaytimePct` = mean of hourly cloud cover over 09–21 UTC.
- [x] Chunking test: 250 fake coordinates → 3 upstream calls, results reassembled in input order.
- [x] Creating a `refresh-weather` instance in tests (`introspectWorkflowInstance` + the binding) completes and writes a `wx:digest:v1` blob matching the spec shape with a fresh `fetchedAt`; on persistent upstream failure the instance errors and the previous KV value is retained untouched.
- [x] Staleness: digest aged >6h → `dataAge.stale: true` + warning; >24h → the stronger warning string; KV key missing entirely → 503 `STALE_DATA_UNAVAILABLE`.
- [x] `/api/windows` responses are served from KV with **zero** weather subrequests at request time (assert via injected fetch fake).
- [x] The `schedules` on both workflow bindings are uncommented and deploy cleanly (the S01-era API gate has lifted — if it still 403s, capture a fresh `cf-ray` from the failing PUT via `WRANGLER_LOG=debug WRANGLER_LOG_SANITIZE=false npx wrangler deploy` and escalate, before falling back to a temporary `triggers.crons` → `create()` bridge).
- [x] Both workflows set explicit per-step `retries`/`timeout` so the worst-case instance lifetime stays under the 2 h cadence (spec 01 overlap caveat).
- [x] Deployed; at least one **schedule-initiated** instance is evidenced (its `WorkflowEvent.schedule` is set / `wrangler workflows instances list` shows the cron trigger source — a manual `wrangler workflows trigger` does **not** satisfy this) and a real response after it shows live forecast dates; the instance's step history is visible via `wrangler workflows instances describe`.
- [x] The per-step measured CPU time is recorded in this story's *Notes* section below; if a single fetch+digest step exceeds ~5 ms at 10 sites, shrink the chunk size (spec 01) before S06 scales to ~250 sites.

Accepted: honest beats fabricated zeros, and the message names the horizon. Revisit with `/api/next-windows` (Slice 4) if it bites.

- **Read path generalized to the 10-site seed list** (`adapters/seed-campsites.ts`): the story's demo line promises windows for 10 campsites, so `service.ts` now scores every seeded site and `core/recommend.ts` groups windows by region — same-(region, start, end) windows merge into one `Window` with member campsites ranked by their own score; the best member defines score/tier/confidence/`daily`. Windows sort by score, ties by soonness. Full ranking with real campsites stays Slice 3. Höfn/Skaftafell are bucketed IS-7 (Austur-Skaftafellssýsla → Austurland, traditional ISO county mapping); S06's point-in-polygon assignment is the durable arbiter. Coordinates are ~1 km accurate — ample for a 2 km model.
- **Fixture recorded** 2026-06-12 via `scripts/record-fixtures.ts` (`node scripts/record-fixtures.ts`, manual only): one real 10-site multi-point response (142 KB) in `test/fixtures/openmeteo/` + `.meta.json`. The contract test pins per-site splitting, 16 consecutive days, units from `daily_units`, and one hand-computed digest day frozen exactly (reykjavik-eco 2026-06-12, cloud mean 26.33 → 26).
- **Daytime cloud convention**: `cloudMeanDaytimePct` = mean of the **12 hourly samples 09:00…20:00 UTC** (the 09–21 window), rounded to an integer. Upstream nulls: a null in any required daily field drops that day; null cloud hours are just excluded (field is optional).
- **Workflow shape**: chunking is computed outside steps (pure, replay-safe); one `fetch chunk i/n` step per ≤100 coords (`retries: 3× exponential from 30 s, timeout: 30 s` → worst case ≈ 5.5 min/step), final `write wx:digest:v1` step stamps `fetchedAt` *inside* the step and is the only KV write — a failed instance never publishes partial data. Tests mock the fetch step via `introspectWorkflowInstance().modify` (`mockStepResult`/`mockStepError` + `disableRetryDelays`), so the write step runs for real against test KV with zero network.
- **Worker test files now run sequentially** (`fileParallelism: false` in `test/worker/vitest.config.ts`): no isolatedStorage in the post-0.13 pool and three files seed/clear the same `wx:digest:v1` key.
- **Zero-subrequest assertion**: tests and the Worker share one isolate in the post-0.13 pool, so the test swaps `globalThis.fetch` for a throwing fake around the request — KV/service-binding calls don't go through it, an Open-Meteo call would.
- **CPU (local, Node 24 desktop — dashboard numbers to be added post-deploy)**: `digestLocations` on the 10-site recorded response ≈ **0.52 ms** + `JSON.parse` of the 142 KB body ≈ 0.16 ms → ~0.7 ms per fetch step at 10 sites; naive 100-site extrapolation ~5–7 ms. Inside the 10 ms step budget, but at S06 scale consider shrinking the chunk or relaxing the zod array validation if the dashboard disagrees.
- **Carried-forward (S03 review)**: confidence/horizon still anchor to `digest[0]` (lead = index + 1). With a 2 h cadence the digest's day 1 is effectively today, so the near-boundary `today+15 → 400` case only appears when refreshes have been failing for a while — acceptable; revisit if `/api/next-windows` (Slice 4) needs an explicit "today" anchor.
